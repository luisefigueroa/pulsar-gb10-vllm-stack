Pulsar GB10 vLLM stack

An operations and evidence control plane for running vLLM on NVIDIA DGX Spark (GB10) machines. Not a vLLM fork. Not a host-native Python server.

Private by construction. This file lives under .local/, which is gitignored. It uses no CDNs, fonts, analytics, or remote images. Open it as file:// on this machine. Do not commit it, gist it, or push it to GitHub Pages if you want the notes to stay private.

What it is

Pulsar launches digest-pinned Docker images. Every launch is gated by an exact model profile whose status had to be earned on this hardware.

The product priority is explicit: stability > accuracy > throughput > latency. Extra discovered Sparks are idle capacity, not permission to invent a new tensor-parallel geometry.

What problem it solves

A GB10 Spark is a Grace–Blackwell box with 121 GiB unified LPDDR5X (no discrete VRAM) and sm_121 kernels. Two of them talk over dual-rail 200GbE RoCE, not NVLink. Decode is memory-bandwidth bound at about 240 GB/s read. Cross-node all-reduce tops out around 21 GB/s because each NIC sits on PCIe Gen5 x4.

Serving that hardware well is not “pick a model and docker run.” Kernel choices, quantization backends, speculative decode, CUDA graphs, and even /health all have GB10-specific failure modes that were measured here. Pulsar is the stack that:

  1. Encodes those measured recipes as models/*.conf
  2. Refuses to launch anything that has not earned STATUS=tested*
  3. Discovers and confirms cluster membership separately from serving geometry
  4. Starts, stops, and inventories only containers it can prove it owns
  5. Keeps a ledger (docs/VALIDATION.md + results/) so every number traces to a run

There is no third runtime. docker-compose.yml is a convenience for one long-lived local server. It does not apply ownership labels, per-model flag arrays, seals, or the status gate. Multi-node never goes through Compose.

A start, end to end

./pulsar start deepseek-v4-flash (or scripts/up.sh deepseek-v4-flash) does this:

  1. Take a shared flock so a concurrent “delete the durable home” cannot race a launch.
  2. load_conf sources models/deepseek-v4-flash.conf into the shell, then checks the profile contract: TP × PP must equal NODES, multi-node must use --distributed-executor-backend mp and a RoCE full mesh.
  3. Status gate. Only STATUS=tested* launches without --force. do-not-use and blocked-upstream stay parked.
  4. For NODES=2, require a confirmed topology (.cluster-topology.json) with enough ranks and rails. Extra confirmed nodes stay idle.
  5. Gates, in order: image on every required rank → weights → memory → cluster/preflight.sh.
  6. Launch:
    • NODES=1 → serve.sh → docker run named vllm-<profile>
    • NODES>1 → cluster/start-cluster.sh → remote headless ranks first, then local rank 0 with the API
  7. Wait on /health (DeepSeek cold load is ~10 minutes), then a real completion smoke. Cluster start also runs validate/warmup.py so the first client does not pay JIT.

serve.sh / start-cluster.sh can be called directly. That bypasses up.sh’s image/weights/memory/preflight gates, but still loads the conf and still enforces status + NODES routing.

Stop is the inverse discipline: down.sh only removes containers labeled io.pulsar.gb10.managed=true with a conf/rank/node placement that maps back to a repo profile. Unlabeled vllm-* names are reported and refused.

Profiles are the policy unit

A profile is a bash file under models/, not JSON. scripts/lib.sh load_conf is the loader. Typical fields:

  • MODEL — Hugging Face id, or an absolute NFS path (/mnt/Models/...)
  • SERVED_NAME — the OpenAI API id (often not the filename)
  • IMAGE — usually digest-pinned
  • NODES, ENGINE_ARGS=(…), CONTAINER_ENV=(…)
  • SPEC_DECODE_ARGS + RECOMMENDED_SPEC — DeepSeek’s DSpark is default-on; Super MTP is opt-in; Qwen GDN has none on purpose
  • STATUS, PROFILE_PURPOSE (serving vs diagnostic)
  • Memory budgets used by check-memory.sh
  • Optional EXPECTED_MODEL_SEAL — a reviewed identity file under models/seals/

Conf filename ≠ API name. Example: nemotron-3-nano-30b-nvfp4 serves as nemotron-3-nano.

Hardware is why the code looks like this

Several “weird” defaults are measured, not taste:

  • --moe-backend marlin on NVFP4 MoE. CUTLASS FP4 is silently wrong on sm_121.
  • CUDA graphs on except official-image cross-node TP=2, which hangs. Workaround is --enforce-eager (Laguna 2-node). The PR-41834 image does not need that for DeepSeek.
  • Never ngram spec on GDN hybrids (Qwen3.6-27B). It corrupts output.
  • Never GDN cross-node. Wrong output, then hang. That is why qwen3.6-27b-fp8-2node is do-not-use.
  • DSpark k=5 is a checkpoint invariant, not a knob. It equals dspark_block_size.
  • /health lies for ~5 minutes after a worker dies. Honest liveness is a 1-token completion. Node loss is teardown + relaunch, not heal-in-place.
  • Ray is not the multi-node path. Validated path is vLLM native --nnodes / --node-rank / --headless with the mp executor over RoCE.
  • MTU 9000, GPUDirect RDMA, and jumbo frames were measured and are not load-bearing.

Memory math is first-class. Unified memory means weights + KV + OS fight for the same 121 GiB. check-memory.sh uses the profile’s WEIGHTS_RAM_GIB / KV_GIB / OVERHEAD_GIB, adds a launch spike for cold start, and never treats a hard FAIL as “continue anyway.”

Three data planes, three weight paths

Even when they touch the same machines, the code treats these as distinct:

  1. Control — SSH, Docker, Gloo rendezvous, wizard
  2. Inference — NCCL over recorded RoCE HCAs (NCCL_NET=IB; no silent fallback to the admin LAN)
  3. Weight transfer — whichever storage policy you chose

Membership lives in gitignored .cluster-topology.json, written by scripts/detect-fabric.sh --write-topology. Schema 2 adds enrolled host keys and .cluster-ssh-config. Hostnames are labels; identity is machine-id + host key. HEAD_IP / WORKER_IP are leftover two-node compatibility only.

1. Replicated local caches — shipped default

scripts/pull-weights.sh downloads the HF tree (exact commit if the profile is sealed), rsyncs it to every serving rank, and up.sh mounts it. Laguna/Inkling are NFS catalog paths; Pulsar will not download those.

This is what the wizard and the README quick start use.

2. Model library / library-hot — implemented, not promoted

One durable home per exact revision. The home rank serves through a symlink (no second full copy). Only non-home ranks get sealed-hot copies under /var/tmp/pulsar-hot. After an unpinned stop you are back to one copy.

Identity is lab-issued, not “whatever is in the local cache”:

  • models/seals/*.json — expected seal (model id, commit, SHA-256 snapshot manifest, provenance)
  • models/validation-bundles/<id>.json — binds image digest, engine args, geometry, evidence
  • A local observed seal may match. It cannot issue a claim.

At launch, a rank-local witness (inode/mtime metadata) can skip rehashing an unchanged tree. Drift causes a visible full SHA-256, or a fail-closed abort. It never auto-reseals.

Preparation (scripts/model-library.sh prepare) moves and verifies bytes. It does not start a container and does not qualify the model. For a reviewed multi-rank profile the fixed experimental policy is 8-stream SSH-over-RoCE, no fallback (ADR 0003). home add creates exactly one sealed durable home; catalog refresh only inventories existing homes.

Why it is not the default: catalog + serving-integration gates passed for DeepSeek; strict determinism on that storage path failed, and soak was not run after that blocker. Replicated remains the guided path.

3. Weight fabric — separate experiment

Long-lived single-copy NFSv4.2/RDMA mount (scripts/weight-fabric.sh). One owner exports; clients hard-mount ro,vers=4.2,proto=rdma with no TCP fallback. The wizard never selects this. Physical promotion matrix is still pending.

Do not call every RoCE-backed thing “fabric.” SSH/TCP over a RoCE IP, one-shot NFS copy, live NFS/RDMA, and NCCL inference are four different systems.

Validation is a product surface

validate/ is not a unit-test folder. It is how a profile earns the right to exist.

ADR 0002 splits evidence so one kind of success cannot launder another:

ScopeWhat it proves
Catalog / artifactExact bytes, placement, transfer, cleanup
Serving integrationMount, load, health, warmup, completion smoke
Model qualificationAccuracy, determinism, throughput, context, soak
Release / promotionConjunction of the above for STATUS, wizard, or a default

A healthy /v1/models is integration, not qualification. Library-hot can pass catalog + smoke and still be blocked as a default. That is the current DeepSeek library-hot situation.

Control-plane tests (scripts/selftest.sh + scripts/testlib/) run without Docker and prove locks, ownership, seals, wizard classification, etc. They do not replace physical gates in docs/REVALIDATE.md.

Language split and ownership rules

The repo is intentionally hybrid:

  • Bash at the operator boundary: CLIs, SSH, docker argv, topology, load_conf
  • Python for schemas, catalogs, digests, budgets, identity, JSON, rendering

Paired modules follow weight-fabric.sh + weight_fabric.py, model-library.sh + model_library.py. Shared kernel is scripts/lib.sh.

Fail-closed is a hard rule. No silent fallback from RoCE to the control LAN, from fabric to a full replica pull, or from “we discovered 3 machines” to TP=3. Destructive ops are confirmation-gated. Privileged sudo never stores a password.

How to think about it day to day

On a Spark head node, the normal loop is:

scripts/doctor.sh
scripts/list-models.sh --validated --serving
./pulsar                          # or ./pulsar wizard
./pulsar start <profile>          # gates + launch
./pulsar status <profile>         # real completion, not just /health
./pulsar stop <profile>

For two-node DeepSeek, confirm topology first (detect-fabric.sh --write-topology), sync the PR-41834 image and weights to both ranks, then start. One-node profiles can be placed on any confirmed idle node with --node <node_id> from inventory --json.

If you later change serving behavior, docs/REVALIDATE.md is the contract: canary, gates, gsm8k, needle, soak, then update the ledger. Selftests cover the control plane only.

The design thesis of the whole tree is: an exact recipe on measured hardware, with a paper trail, and no silent “make it work.”
